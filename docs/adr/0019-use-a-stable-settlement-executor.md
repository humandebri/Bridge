# Settlement実行をstable SQLite job queueへ集約する

[ADR 0023](0023-use-wallet-funded-eip712-mint-authorization.md)のEIP-712 Mint Authorizationと、ADR 0018のFinalized保証およびユーザー実行Withdrawalを前提とする。

`settlement_jobs`をSettlement実行状態の正本とする。Depositとfee payoutではone-shot timerがSQLiteから期限到来jobをclaimする。Withdrawalはtimerで実行せず、明示的な`continue_withdrawal`ごとにjobをmanual claimする。timer IDやheap上のin-flight集合へ永続的な意味を持たせない。

claimはrecord単位のleaseと単調増加するgenerationをSQLite transactionで取得し、RPC、署名、Ledger呼出しの直前にleaseを更新する。await後のcheckpointは同じgenerationだけを受理する。期限切れleaseを回収した後に古いcallbackが戻っても、外部結果でstable stateを上書きできない。Automatic、Public Manual、Governance Recoveryのlaneごとに同時実行上限を持ち、同一recordのleaseは重複させない。

Depositとfee payoutはrecordとjobを同じtransactionで作成または更新する。Withdrawal通知は`ReleasePending` recordと固定Ledger transfer identityだけをatomic保存し、jobを自動登録しない。明示継続時にはjobを作成または再claimする。DepositではAuthorizationの署名dispatch、作成元Finalized snapshot、固定deadline、digest、service fee確定をjobの進行と一貫して保存する。期限後の予約解放はdeadline indexをローカル走査し、Refund請求時の失効・Mint証拠とLedger transfer identityはownerの明示操作で保存する。Withdrawalとfee payoutではLedger transfer identityを外部呼出し前に保存し、Ledgerの冪等性またはDuplicate応答から回収する。停止、延期、完了は現在のlease generationだけがfenced outcomeとして保存できる。

新規受付後のAuthorization生成と`continue_withdrawal`は同じrunnerとfencingを使用するが、Withdrawalを自動dispatchしない。任意の非anonymous Principalが呼べる`continue_withdrawal`は、既存quotaとcycles floorを満たす場合だけ、Ledger送金または履歴照合を最大1 external step進める。完全な不存在を確認して新identityを保存した場合、その送金は次の明示呼出しへ分離する。非終端結果とstaleなscheduled Withdrawal jobは`Stopped`へ退避する。Deposit refundは`request_deposit_refund`だけが起動し、通常の有効leaseを迂回せず、任意の非anonymous Principalがrate limit・strict deadlineを満たす場合だけclaimする。返金先・金額・transfer identityは既存recordからのみ取得する。認可発行後はBase Finalized timestampとcanonical blockへ束縛した`isDepositProcessed`照合を必須とし、早期返金を許可しない。

Mint用Base transaction laneは持たない。Governance Operatorのnonce、署名済みraw transaction、generationは`settlement_jobs`から分離したGovernance署名laneで扱う。broadcast、Finalized receipt待機、確定通知は外部relayerの責務とし、Canister timerによるrebroadcast・receipt監視・自動replacementは行わない。replacementはGovernanceが明示した場合だけ同一payload・nonceへ署名する。

public scheduler healthはjob件数とdispatcher diagnosticsから導出する。degraded/faulted表示は運用判断の情報であり、個別jobの実行可否を決めるglobal gateにはしない。
