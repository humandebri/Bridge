# Bridge verification ledger

Lean is the authoritative abstract protocol specification; generated vectors check bounded conformance with production consumers.
No complete semantic refinement is claimed for the implementation, including inputs or side effects not enumerated in those vectors.

Read each claim's abstract Lean proof, finite-width model refinement, Verus implementation basis, SMT obligation, Halmos obligation, production symbol, transaction test, and external assumptions independently. In the Verus manifest, `executable` binds the production function's return value to the proof's named return and `ensures`; `shared-expression` structurally checks a registered single-arm macro, positional parameters, integer constant aliases, and explicitly registered derived inputs, and references the corresponding predicate spec from `ensures`; `derived` binds `ensures` to a separately written or composed spec; and `model` is a model proof without a production symbol. These four classes do not have equal strength. Every Verus obligation declares its supported claims, exactly matching references from the claims ledger. The required production-bound Verus evidence set must exactly match the claim's `implementation_basis`. A whole claim is implementation-proved only if every Verus obligation is directly production-bound or is `derived` solely from production-bound `executable` / `shared-expression` obligations of the same claim. SMT obligations support partial properties of production-shared kernels; Halmos obligations support partial properties of the post-auth commit boundary. Both must remain `supporting`, never evidence for the entire public Bridge wrapper or deployed contract. AST checks bind the wrapper-to-commit call through the source of `digest`, declaration IDs used for signature recovery, every `evaluateMint` input field and the source of `effects`, absence of reassignment, and declaration IDs and ordering of commit arguments. Production transaction tests cover concrete paths from authentication through events and persistence.
`claims.tsv` is authoritative for the closed release claim set, `assurance_target`, `required_strength`, trace theorems, Verus obligations, production symbols, transaction selectors, and assumption IDs; descriptions in this table alone do not establish completion. The audit evidence matrix is schema 7 `verification/output/claim-report.json`, which distinguishes `abstract-proved`, `production-linked`, and `implementation-proved` and reports `release-blocked` separately from external assumptions. The five conditional liveness results in `conditional-liveness.tsv` are auxiliary theorems, not release claims.
`assumptions.tsv` is authoritative for each external assumption's dependent claims, testable fault cases, operational monitoring, and fail-closed behavior when violated.
