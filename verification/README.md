# Bridge verification boundary

The Lean project is the formal abstract specification of the cross-chain protocol.
State transitions, invariants, frontend decisions, and pending queue updates are centralized in `verification/lean/BridgeSpec`, with theorems checked by Lake.
Rust, Solidity, and TypeScript consumers read `verification/generated/protocol-vectors.json`, generated by the Lean executable, and compare representative implementation boundary cases against the same expected results.
Release claims are defined in `Claims.lean`, finite-width models in `FiniteWidthModel.lean`, correspondence with the abstract model in `ModelRefinement.lean`, and integrated state traces and certificates in `Protocol.lean`. `ModelRefinement` provides the model-side basis for bounded conformance through generated vectors; it is not production refinement.
Schema 7 of `verification/claims.tsv` is a typed manifest for protocol and Mint Authorization claims, `assurance_target` (`release-safety` / `model-support`), `required_strength`, Lean theorems, Verus obligations, SMT/Halmos obligation IDs, explicit implementation bases, production symbols, vector sections, and external assumptions. Claim-to-transaction-test links are maintained separately in `verification/claim-test-links.tsv` (three columns: claim ID / target / symbol) and must exactly match test execution registrations. Schema 7 has 12 columns after removal of the old transaction-test column; it is independent of the Canister stable schema. For the current 43 claims, the 25/18 partition of targets and minimum strengths must exactly match the checker's fixed policy, preventing manifest-only downgrades out of audit scope or swaps of minimum strengths. All SMT and Halmos obligations are `supporting` and cannot independently promote a whole claim to `implementation-proved`. That strength requires a proved Lean contract, an exact match between the required production-bound Verus evidence set and `implementation_basis`, and coverage of every Verus obligation either as production-bound or as `derived` evidence depending only on production-bound `executable` / `shared-expression` evidence for the same claim. Production symbols and transaction tests alone yield `production-linked`; abstract proofs alone yield `abstract-proved`. Any `model`, unbound obligation, or unresolved derived obligation prevents promotion. `scripts/check_claim_manifest.py` computes schema 7 `verification/output/claim-report.json` and fails the gate with `release-blocked` when a `release-safety` claim lacks its Lean contract, required strength, production symbol, or transaction test. External assumptions are displayed separately from status.
`verification/proof-impact.tsv` maps safety-related production sources to claims and required proof stages. `scripts/check_proof_impact.py` fails closed if a Rust or Solidity source in a watched root is unregistered, a claim's production source lacks an owner, or the proof receipt's source fingerprint differs from current sources and proof materials. The fingerprint conservatively includes production sources, proof consumers and tests (including PicJS integration), drivers, toolchain/build/test settings, and lockfiles, excluding generated outputs, build caches, `.venv`, and the explicitly listed advisory-only Certora inputs. Verification documents, including `obligations.md`, are fingerprinted. A schema 8 receipt fixes the fingerprint at proof startup and requires the same value before and after each required stage, around claim evidence generation, and at final verification. A receipt is accepted as complete only when every stage passes exactly once in order with that fingerprint, all 43 claims are release-ready, release-blocked and model-support counts are zero, evidence strengths are 25 implementation-proved and 18 production-linked, and there are five conditional-liveness entries. `halmos-and-negative` requires every positive case to be proved in the locked environment and each mutant to return exactly one counterexample. `claim-transaction-tests` checks that every test registered in `verification/claim-test-manifest.tsv` passes exactly once. Changes for which the existing theorem still applies do not require cosmetic proof-file edits; they require rerunning all stages against current sources.

The receipt summary records the total claim count and counts for `release-ready`, `release-blocked`, `model-support`, `conditional-liveness`, `implementation-proved`, `production-linked`, and `abstract-proved`. Obsolete receipt schemas are rejected.

Safety claims for the changed Mint Authorization path are split in the same manifest into authorization binding, expiry refund, exact mint finalization, epoch invalidation, reservation lifecycle, fee accounting once, deposit backing, and manual claim exclusion. Cryptographic known-answer tests are managed separately in `verification/known-answer-manifest.tsv` and are not promoted to Lean-generated policy evidence.
CI checks exact coverage of all Lean theorems, Verus manifests, claim ledger entries, vector sections, and consumers. Verus proof names must be unique. Non-executable proofs reference their registered spec from `ensures`; executable proofs constrain a named return in `ensures` and return the registered kernel call as their final expression. Production call sites are restricted to Rust production roots. Solidity proof links resolve uniquely to compiler AST contracts and complete overload signatures. `referencedDeclaration` checks direct calls from SMT passes to production kernels and from the Bridge wrapper to the post-auth commit boundary. The Bridge wrapper derives `digest` from `_mintAuthorizationDigest(authorization)`, recovers the signer using the same `digest` and `signature`, and derives `effects` from the sole `evaluateMint` call receiving a `MintTransitionInput` with all 18 fields bound to declaration IDs. Neither variable may be reassigned; the commit receives `authorization`, `digest`, and `effects` in that order with the same declaration IDs.
The refinement manifest has five columns: section, abstract definition, finite-width model definition, model refinement theorem, and runner. Multiple consumers may be registered for a section. Explicit per-runner renderers deterministically generate consumer sources, test selectors, and production calls; generated artifacts are tracked in Git.
CI permits only the approved Rust, Foundry, and Vitest runners. It rejects incomplete manifest/renderer coverage, generated drift, and selectors duplicated by non-generated tests, then verifies that each selector passes exactly once. Production links express ownership; the presence of a string does not increase proof strength.
Vector comparisons establish bounded conformance for the enumerated cases, not complete semantic refinement of the Rust, Solidity, or TypeScript implementations.

Withdrawal verification covers the irreversible `Committed` burn on Base and outstanding Canister liabilities. The model has no Base refund, release acknowledgement, or Withdrawal EVM operation.

The five conditional liveness results are excluded from the release claim catalog. Their Lean theorems remain auxiliary results; fully qualified theorem names, proposition types, and strong fairness, external resolution, and action admissibility assumptions must exactly match the checker's fixed policy. The proof gate typechecks each theorem against its expected proposition type and checks axiom dependencies against the same allowlist as claim witnesses. Production-unbound boundaries are recorded in `conditional-liveness.tsv` and `conditional-liveness.md`.

- Foundry checks reversion before burn on fee drift, fixed quotes, atomic burns, and replay rejection for processed Deposit IDs. The ABI snapshot checks that no Withdrawal-specific refund/remint selector exists.
- Typed decisions for settlement, deposit admission, deposit identity preflight, reservation, fee recipient rotation, fee payout, hold resolution, lease outcome, and manual claim use the same executable function bodies in Cargo and Verus. Verus directly checks result variants, every delta field, and boundary rejections. A manifest `shared-expression` obligation is a predicate proof in which a Cargo expression and Verus spec each invoke a registered single-arm macro exactly once, with matching direct parameter positions, argument counts, and integer constant aliases. Production-derived expressions form the predicate input boundary corresponding to arbitrary spec inputs; this is not a proof of the entire executable function. `derived` denotes a separately written spec or a composition proof over multiple kernels and does not independently establish a production implementation proof. `model` has no production binding.
- `bridge-core/src/kernel.rs` also shares snapshot refresh ownership, reserve observation tokens, settlement lease generations, canonical probe block equality, and derived index classification for Withdrawal and reconciliation holds with production. Verus checks each predicate.
- Lean formally models Base supply reduction and Canister liability creation, payment to fixed destinations, 1:1 backing, frontend Finalized success/revert/retry decisions, and serialized queue updates.
- Rust/integration checks canonical Finalized matching, Ledger success/Duplicate/BadFee/ambiguous outcomes, net Fee reserves, and the absence of additional EVM transactions.

Solidity SMT establishes properties of production-shared predicates; Halmos establishes state, token, and rollback properties at the commit boundary after signature authentication. Neither proves the public wrapper or the entire deployed contract.
The frontend Lean model does not prove the TypeScript implementation itself. Tests check correspondence between generated vectors and pure decision functions.
The Bridge Signer signs EIP-712 Mint Authorizations. A compromised Signer can create valid authorizations for unprocessed Deposit IDs; epoch invalidation, pause, fixed limits, and the mint window bound the rate of damage.
Correctness of EIP-1898 `requireCanonical`, EVM rollback and EIP-1153 transient storage lifetime, the ABI decoder, Web Locks, browser storage, provider `finalized` semantics, provider response authenticity, wallets, ICRC history authenticity, SQLite atomicity, and SQL row selection are external assumptions. The predicate selecting an exact 2-of-3 identity from decoded `(block number, block hash)` values uses the same expression in the production-shared kernel and Verus. Formal proofs cover this selection, post-decode block equality, enum-to-derived-index classification, and queue state after a successful browser storage update.
Bridge runtime immutability is an external assumption. A production-shared predicate and Verus check the conditions for reusing a stored observation as warm attestation. Rust and PocketIC transaction tests cover persistence after cold success, reuse across paths, and upgrade/reinstall boundaries.
Verus/Rust/LLVM, the Lean kernel, Solidity SMTChecker, Halmos/Z3, and the Wasm compiler form the trusted computing base. Source-level proofs are not Wasm binary verification.
If the fixed Ledger Fee of 100,000 raw exceeds the charged Service Fee, the fixed fee guard stops processing before release. The same record is revalidated after pausing Base withdrawals and checking configuration. Ledger Fee immutability is an external assumption; runtime settlement does not query `icrc1_fee()`.

Lean's `step` has no post-filter based on `Safe next`. `raw_step_preserves_safe` directly proves safety for each accepted raw transition, and the finite-trace theorem follows by induction from that lemma. Canonical and Ledger certificates include the target identity, but authenticity of their history and RPC information remains an external assumption.

Rust transaction tests and same-Wasm PocketIC tests validate schema v36 reopening and wire v30. Only production and test-deployment post-upgrade paths accept the one-time atomic migration from deployed schema v35 to v36; all other old or unknown schemas fail closed.

## Production-equivalence definition

Production-equivalent validation does not mean the entire production implementation is formally verified. Each claim distinguishes `abstract-proved`, `production-linked`, and `implementation-proved`, with external assumptions and the TCB disclosed separately. TCB correctness is an assumption outside the proofs and cannot be eliminated by them.

Production-equivalent validation is defined by the following conditions:

1. The release proof gate passes directly from a clean checkout (see below).
2. Every `release-safety` claim meets the evidence strength required by the manifest, with zero `release-blocked` claims.
3. External assumptions are registered in `verification/assumptions.tsv`, including dependent claims, fault tests, operational monitoring, and fail-closed behavior.

## Release proof gate

### Claim transaction-test execution

`verification/claim-test-manifest.tsv` requires five columns: `runner / target / symbol / selector / execution`. `execution` is either `grouped` or `isolated:<reason-slug>` with a reason. The obsolete four-column format is rejected. Tests sharing a runner, configuration, and file are grouped; Rust's normal and test-deployment features remain separate. Rust resolves fully qualified names uniquely from the test list and runs them serially with exact filters; JavaScript and Foundry results are checked against structured reports. Missing, skipped, duplicate, failed, unparseable, or wrong-file results for required tests are rejected. Only skips of unselected JavaScript tests are allowed.

`python3 scripts/check_claim_test_manifest.py --plan-only` displays claims, tests, groups, runner invocation counts, and required builds before execution. `--validate-only` checks registrations only. `proofs-impacted` passes generated impact JSON through `--impact-json` and runs only the union of required tests for affected claims. Wasm dependencies are not prepared unless Jest is selected. Full `proofs` passes no selection arguments and runs every registered test; partial runs cannot issue a complete proof receipt.

Self-reported proof attestations are not used.
Immediately before irreversible operations, the fixed production driver directly runs `scripts/ci-local.sh proofs` in the clean checkout bound to the manifest.
Release stops if HEAD, archive tree hash, worktree, or submodule revisions differ before and after execution, or if the proofs fail.
A Gate bundle containing `proof-attestation.json` is also rejected because that artifact is obsolete.
After proofs pass, the Bridge Canister Wasm and Bridge contract runtime are each built offline twice from the same clean revision. Irreversible operations require exact SHA-256 agreement between both builds and the release manifest.

This gate checks reproducibility within a trust boundary of fixed local sources and toolchains. It does not establish third-party CI provenance, compiler correctness, or semantic equivalence between source and binary.

`verification/output/proof-receipt.json` is generated by the proof gate and is not tracked in Git. Its source fingerprint fixes the working tree at execution startup; rather than matching a tracked-source snapshot, `ci-local.sh proofs` itself requires all stages to pass with the same fingerprint and reach `complete: true` within the release gate. Because the receipt is gitignored, its fingerprint is not expected to match committed content. Neither `proof-attestation.json` nor the receipt itself is included in the Gate bundle. Receipts with a mismatched fingerprint, incomplete stages, or non-pass stages fail closed and require a rerun.

## Test execution results within one gate

Each invocation of `all`, `proofs`, or `proofs-impacted` uses one `execution_session.py` process to start tests and retain successful execution results. Claim, refinement, and known-answer stages may reuse the same tests already executed within that invocation. Results cannot be imported from another invocation, job, saved JSON, or partial receipt. `all` shares complete runner suites; proof-only runs share selected files (feature-specific libraries for the Rust Canister). `bridge-profile` runs only the union of selectors registered for proofs; the regular full suite runs under `all`. `isolated` registrations cannot be shared and fail without a dedicated execution plan.

Receipt schema 8 stores the run ID, HEAD, trusted base (when configured), tool versions, submodule revisions, environment digest, consumed Wasm digest, execution commands, native report digests, and stage-to-test mappings. Source changes, missing/duplicate/skipped/failed tests, or different Wasm artifacts cause failure. Native stdout/stderr are saved under `verification/output/test-execution/<run-id>/`. A complete proof receipt still requires all 10 stages; verification also requires agreement with current sources, HEAD, tools, submodules, and Wasm.

## Proposition semantics and change review

`claim-semantics.tsv` records premises, conclusions, specification references, and unproved boundaries for 43 release claims and five conditional liveness results.
`definition-semantics.tsv` centralizes the meanings of major definitions, distinguishing specification definitions from supporting model definitions.
Evidence and external assumptions reference the existing claim ledger; these tables introduce no additional evidence-strength classification.

`python3 scripts/check_claim_semantics.py --write` generates JSON and Markdown containing proposition types and major definitions interpreted by the pinned Lean version.
The generated artifacts, `verification/generated/claim-statements.*`, exclude witness proof bodies.
Normal execution rejects generated artifact drift.
This check is part of the existing claim-manifest stage and does not change the receipt's 10 required stages.

Trusted CI compares against the existing trusted base commit.
Claims with changed propositions or major definitions require correspondence-table updates; source-only changes are also reported for review.
Review source diffs for type/structure internals and dependent definitions outside the major-definition list.
Matching hashes, matching theorem names, or a candidate updating its own snapshot do not prove semantic agreement with the specification.
`verification/` remains subject to the existing exact-head review requirement; updating both snapshots and correspondence tables cannot bypass review.

See the [proof outline](proof-outline.md) for the reading order and limits of the proofs.
Deposit history is defined in `DepositHistory.lean`, individual policies in `ProtocolPolicies.lean`, and integrated transitions and preservation theorems in `Protocol.lean`.
GlobalHistory's `AccountingInvariant` constrains accounting and record structure; it does not derive completion of an actual transfer from a terminal phase.
The integrated Protocol's `filterSafeStoredState` is also an abstract acceptance condition, not an implementation proof of production decoding or migration.

## Audited implementation boundaries

UI `.ts` and `.tsx` sources are watched roots. Every source must have claim/stage ownership or a reviewed exact-file exclusion with a reason. Presentation exclusions do not establish safety evidence. The four excluded ABI/Candid outputs remain subject to mandatory codegen checks in UI validation and proof preflight. New unregistered UI sources fail closed in both proof ownership and CI classification. The source fingerprint still includes excluded UI sources.

Verus production call sites are resolved through active module declarations and the reviewed production cfg (Wasm canister/core, native profile tool, no test-deployment). Inactive test functions and call blocks cannot establish production binding; unsupported conditions are rejected. `audit_next` binds to production audit preparation and append paths.

`governance_transaction_affordability` binds both the conservative minimum of Finalized/Safe balances and the inclusive acceptance comparison to one shared-expression kernel decision. The checked transaction liability calculation is a separate required obligation. External balances and fee adequacy remain assumptions. The signing/paid-call reserve, automatic retry, and cycles top-up claims retain their own registered kernels and documented boundaries; their labels do not prove entire asynchronous adapters.

The claim vector column is a semicolon-separated list of refinement sections (or `-`). `lease_lane_isolation` owns both `lease_lane_cases` and `manual_claim_cases`; every section retains its registered generated consumer. Receipt schema 8 remains independent of claim schema 7.

Production cfg resolution also checks the reviewed Cargo feature graph. `storage-serde` is enabled only for bridge-core in the canister build, not for every Wasm crate; changed default or dependency features require an explicit review of this binding.
